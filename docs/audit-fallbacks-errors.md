# Аудит обработки ошибок и заглушек (Fallbacks)

Дата: 05.10.2026 · Объём: весь репозиторий — `server.js`, `db/`, `core/` (ELLA AI), `config/`, `client/src/` (React).
Микросервисов, очередей и кэша нет: один процесс Node.js + SQLite (`better-sqlite3`) + SPA на React.

**Методика.** Статический разбор каждого файла (все `fetch`, `async`, `catch`, дефолтные значения, ветки `if (!data)`), затем динамическая проверка: сервер запускался на временной БД с внедрёнными сбоями — неверный ключ OpenAI, отсутствующий ключ, блокировка записи в SQLite, битый JSON, превышение лимитов загрузки, запрос без авторизации. Результаты прогонов приведены в карточках с пометкой «Проверено».

> **Статус исправлений (05.10.2026).** Все проблемы уровня High закрыты, а вместе с ними и часть связанных Medium/Low. Регрессия: `npm run verify:shop` — 29/29.

## 1. Итоговый свод (Executive Summary)

**Оценка устойчивости: 6 / 10.**

Базовый каркас надёжный: есть Error Boundaries на всех уровнях, глобальный обработчик ошибок Express, транзакции SQLite откатываются автоматически, блокировка БД не роняет сервер (проверено). Основные риски — **тихие подмены**: чат ELLA при любом сбое ИИ выдаёт шаблонные ответы как будто от ИИ, админка показывает «пусто» вместо ошибки загрузки, а сбои OpenAI вообще не попадают в логи. Плюс одна точка, способная уронить весь процесс (таймер очистки сессий).

| Критичность | Кол-во |
|---|---|
| Critical | 0 |
| High | 4 |
| Medium | 12 |
| Low | 11 |
| **Всего** | **27** |

**Что сделано хорошо** (менять не нужно):

- `ErrorBoundary` стоит на корне приложения, на каждой странице (с `key` по маршруту, т.е. ошибка на одной странице не ломает переход на другую), отдельно на чате ELLA и на админке — «белого экрана» при падении компонента нет.
- Транзакции `better-sqlite3` (`createOrder`, `updateOrderStatus`, `deleteOrder`, `updateService`) атомарны и откатываются при исключении.
- **Проверено:** при занятой записи в SQLite `POST /api/orders` ждёт `busy_timeout` (≈5,5 с), отвечает `500 «Не удалось сохранить заявку»`, ошибка `SQLITE_BUSY` пишется в лог, сервер продолжает работать.
- **Проверено:** битый JSON → `400 «Некорректный запрос»` (глобальный обработчик `server.js:995`).
- `adminApi` и `saveOrderToServer` различают сетевую ошибку и не-2xx статусы; форма заказа показывает ошибку и закрывает заранее открытую вкладку мессенджера.
- Вызов OpenAI имеет таймаут 25 с и повтор на 429/502/503; ошибки инструментов ELLA перехватываются в `registry.execute`.

## 2. Реестр найденных заглушек (Fallbacks & Mocks)

### F1 · High · Имитация ИИ-ответа при сбое API

- **Файл и строка:** `client/src/components/EllaChat.jsx:356-390` (логика), `:67-118` (`replyTo`)
- **Тип:** Simulated API
- **Описание:** при **любом** неуспешном ответе `/api/ella/chat` (нет ключа, исчерпана квота OpenAI, лимит 30 сообщений/15 мин, 500, обрыв сети) чат молча переключается на локального бота на регулярных выражениях и показывает его ответ в том же пузыре от имени ELLA. - **Пример кода:**

## 3. Реестр проблем с обработкой ошибок

### E1 · High · Падение процесса из таймера очистки сессий

- **Файл и строка:** `server.js:92`
- **Тип проблемы:** Unhandled exception (timer callback)
- **Сценарий сбоя:** раз в час выполняется запрос к SQLite без `try/catch`. Если в этот момент база занята дольше `busy_timeout` (бэкап, долгая транзакция) или диск переполнен, исключение из колбэка таймера становится `uncaughtException` → **процесс Node завершается, сайт недоступен** до ручного перезапуска. Глобальных обработчиков `process.on("uncaughtException" | "unhandledRejection")` и корректного завершения по `SIGTERM` нет.
- **Основание:** динамически подтверждено, что та же операция при блокировке бросает `SqliteError: database is locked (SQLITE_BUSY)`; внутри HTTP-запроса её ловит Express, внутри таймера — никто.
- **Фрагмент кода:**

```js
setInterval(() => store.pruneSessions(), 60 * 60 * 1000).unref?.();
```

### E2 · High · Сбои ИИ не логируются

- **Файл и строка:** `server.js:572-576`
- **Тип проблемы:** Silent fail
- **Сценарий сбоя:** все ошибки OpenAI (неверный/истёкший ключ, квота, таймаут, 5xx) возвращаются клиенту, но **не пишутся в лог**. Вместе с F1 это означает: ИИ может не работать неделями, и никто этого не заметит.
- **Проверено:** после ответа `502` на неверный ключ лог сервера пуст.
- **Фрагмент кода:**

```js
} catch (error) {
  if (error instanceof EllaError || error?.name === "EllaError") {
    return res.status(error.status || 500).json({ error: error.message });
  }
  res.status(500).json({ error: error.message || "Сбой AI-консультанта" });
}
```

### E3 · Medium · Утечка внутренних сообщений посетителю

- **Файл и строка:** `core/llm.js:54-59`, `server.js:574`, `:576`, `core/errors.js:12`
- **Тип проблемы:** Information disclosure
- **Сценарий сбоя:** текст ошибки OpenAI и любой непредвиденной ошибки уходит в публичный ответ как есть. Посетитель видит детали инфраструктуры.
- **Проверено:**
  - неверный ключ → `502 {"error":"Incorrect API key provided: sk-audit*****0000. You can find your API key at https://platform.openai.com/..."}`
  - без ключа → `503 {"error":"AI-ключ не найден. Добавьте OPENAI_API_KEY в файл .env"}`
- **Фрагмент кода:**

```js
const detail = payload?.error?.message || "Ошибка OpenAI API";
// ...
throw upstream(detail, payload?.error);
```

### E4 · Medium · Нет общего дедлайна для запроса к ИИ

- **Файл и строка:** `core/config.js:9-12`, `core/llm.js:36-82`, `client/src/components/EllaChat.jsx:356`
- **Тип проблемы:** Missing timeout
- **Сценарий сбоя:** одна реплика — до 4 циклов инструментов × (25 с + повтор 25 с) ≈ **200 с**. На клиенте `fetch` без `AbortController` и таймаута: пользователь минутами смотрит на «печатает…», а при уходе со страницы запрос не отменяется.
- **Фрагмент кода:**

```js
const response = await fetch("/api/ella/chat", { method: "POST", body: formData });
```

### E5 · Medium · Вечный индикатор «печатает…» и проглоченная ошибка

- **Файл и строка:** `client/src/components/EllaChat.jsx:306-308`, `:406`
- **Тип проблемы:** Silent fail / Empty catch
- **Сценарий сбоя:** `setTyping(false)` вызывается в конце `runAsk`, а не в `finally`. Любое непредвиденное исключение до этой строки (например, при сборке превью файла) оставляет «печатает…» навсегда, а цепочка `.catch(() => {})` молча проглатывает ошибку: ни сообщения пользователю, ни лога.
- **Фрагмент кода:**


## 4. Рекомендации по исправлению

Порядок: сначала High (E1, E2, F1, F3), затем Medium.

### 4.1 E1 — защитить фоновые задачи и процесс

```js
function runSafely(name, fn) {
  try {
    fn();
  } catch (error) {
    logError(`job:${name}`, error);
  }
}
setInterval(() => runSafely("prune-sessions", store.pruneSessions), 60 * 60 * 1000).unref?.();

process.on("unhandledRejection", (reason) => logError("unhandledRejection", reason));
process.on("uncaughtException", (error) => {
  logError("uncaughtException", error);
  process.exit(1); // состояние неизвестно — перезапуск через pm2/docker restart
});

const server = app.listen(PORT, /* ... */);
server.on("error", (error) => {
  console.error(error.code === "EADDRINUSE" ? `Порт ${PORT} занят` : error);
  process.exit(1);
});
process.on("SIGTERM", () => server.close(() => { store.closeDatabase(); process.exit(0); }));
```

Запускать в продакшене только под менеджером процессов с автоперезапуском (`pm2`, `systemd`, `docker --restart unless-stopped`).

### 4.10 E8 — скачивание PDF с обработкой ошибок

```js
export async function downloadPdf(url, fallbackName) {
```
