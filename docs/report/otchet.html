1. Введение

Объектом работы является веб-сайт «Клиника доктора Сулейменова» — сайт семейной стоматологии в Астане с каталогом услуг и товаров, корзиной, оформлением заявок, административной панелью и встроенным ИИ-ассистентом ELLA. Сайт предназначен для реальной эксплуатации, поэтому основное внимание в работе уделено не только функциональности, но и надёжности: корректной работе при сбоях внешних сервисов, понятным сообщениям об ошибках и простоте развёртывания.

Цель работы — довести проект до состояния, пригодного для эксплуатации (production): найти и устранить ошибки в логике заказов и в обработке сбоев, а также упаковать приложение в Docker-контейнер для переносимого развёртывания.

Задачи:

  1. Проверить корректность и надёжность работы товаров, остатков и заказов.
  2. Провести сквозной аудит обработки ошибок и «заглушек» (fallbacks) на клиенте и сервере, оценить устойчивость системы и составить реестр проблем.
  3. Исправить найденные проблемы в порядке критичности.
  4. Покрыть исправления автоматическими тестами.
  5. Упаковать проект в Docker с сохранением данных между перезапусками.

2. Описание проекта

Сайт состоит из публичной части (витрины) для посетителей и закрытой административной панели для владельца клиники.

2.1. Публичная часть

  • Главная страница — информация о клинике, популярные услуги, частые вопросы, контакты, карта (2ГИС).
  • Каталог — услуги и товары с фото, ценой и остатком; цены могут задаваться в тенге, долларах, евро или рублях и автоматически пересчитываются в тенге по актуальному курсу.
  • Корзина и заявка — посетитель указывает имя и телефон, заявка сохраняется на сервере, после чего открывается WhatsApp или Telegram с готовым текстом заказа.
  • ИИ-ассистент ELLA — чат на базе OpenAI. Отвечает на вопросы о клинике, ценах и услугах, получая данные из каталога через механизм инструментов (function calling: get_catalog, get_service, get_clinic_info). Посетитель может прикрепить фото.
  • PDF-каталог — выгрузка каталога в PDF для отправки клиенту.

4. Проверка готовности магазина к эксплуатации

На первом этапе была проверена логика товаров и заказов. Для каждой операции проверялось, что произойдёт при одновременных запросах, некорректных данных и злоупотреблениях. В результате в системе действуют следующие механизмы защиты:

МеханизмКак работает
Атомарное списание остаткаОстаток уменьшается внутри транзакции SQLite (BEGIN IMMEDIATE) с условием quantity >= qty. Два покупателя не могут купить последний товар одновременно. Отмена или удаление заказа возвращает остаток.
Ограничение количестваНе более 10 штук одной позиции (настраивается) и не более 30 позиций в заказе.
Проверка телефонаНомер нормализуется и проверяется на правдоподобие; не более 3 открытых заказов на один номер.
Цена считается на сервереКлиент передаёт только идентификатор и количество; цена и сумма берутся из базы, поэтому подменить цену из браузера нельзя.
ИдемпотентностьПовторная отправка той же заявки (заголовок Idempotency-Key) не создаёт дубликат.
Ограничение частоты запросовЗаявки — 12, сообщения ELLA — 30, попытки входа — 10, PDF — 30 запросов за 15 минут с одного IP.
БезопасностьПолитика CSP, cookie httpOnly/SameSite/Secure, запрет слабых паролей в production, доверие к заголовку X-Forwarded-For только при явной настройке TRUST_PROXY.

5. Аудит обработки ошибок и заглушек

5.1. Методика

Аудит проводился по техническому заданию «Сквозной аудит обработки ошибок и заглушек (Fallbacks)» и охватывал весь репозиторий: сервер, базу данных, ядро ИИ, конфигурацию и React-клиент.

  1. Статический анализ — просмотр каждого файла: все сетевые запросы, асинхронные функции, блоки catch, значения по умолчанию, ветки «если данных нет».
  2. Динамическая проверка — запуск сервера на временной базе с искусственно внедрёнными сбоями: неверный и отсутствующий ключ OpenAI, блокировка записи в SQLite, некорректный JSON, превышение лимитов загрузки файлов, запросы без авторизации.

Каждая проблема заносилась в реестр с указанием файла и строки, типа, сценария отказа и примера кода. Полный отчёт аудита находится в файле docs/audit-fallbacks-errors.md.

5.2. Результаты

Исходная оценка устойчивости — 6 из 10. Базовый каркас оказался надёжным (обработчики ошибок React на всех уровнях, глобальный обработчик Express, автоматический откат транзакций), но были найдены «тихие подмены» — ситуации, когда система при сбое показывает правдоподобные, но ложные данные, и никто об этом не узнаёт.

6. Исправление найденных проблем

Исправления выполнялись в четыре этапа, от более критичных к менее критичным. После каждого этапа запускались автотесты, а их набор расширялся проверками нового поведения.

6.1. Этап 1 — проблемы уровня High

  • Устойчивость процесса: фоновые задачи обёрнуты в безопасный запуск; добавлены глобальные обработчики unhandledRejection / uncaughtException, понятное сообщение при занятом порте и корректное завершение (SIGTERM/SIGINT) с закрытием базы.
  • ELLA: шаблонный «бот-заглушка» удалён. При сбое чат честно сообщает об ошибке и предлагает кнопку «Повторить» и ссылку на WhatsApp. Ошибки OpenAI пишутся в журнал, а посетитель получает общий текст без технических деталей.
  • Счета: без заполненных реквизитов сервер не формирует счёт и возвращает понятное сообщение (HTTP 503).

6.2. Этап 2 — административная панель и журналирование

  • Истёкшая сессия переводит админку на форму входа с сообщением «Сессия истекла».
  • У списков товаров и заказов появились состояния «загрузка» и «ошибка» с кнопкой «Повторить» — раньше при ошибке показывалось «Пока пусто», что провоцировало создавать дубликаты товаров.
  • Кнопка «Сохранить» блокируется на время запроса — исключена двойная отправка формы.
  • Ошибки скачивания PDF показываются человеческим текстом, а не сырым JSON.
  • Централизованное журналирование: сервер пишет ошибки в формате JSON с уникальным идентификатором запроса (requestId), методом, путём и IP. Ответ с ошибкой 500 содержит этот идентификатор, и администратор видит его как «код ошибки». Ошибки из браузера (падения React, необработанные исключения) отправляются на сервер и попадают в тот же журнал.

6.3. Этап 3 — курсы валют, тайм-ауты ИИ, витрина

  • Курсы валют (модуль lib/rates.js): раньше курсы были зашиты в код (480/520/5,2) и молча устаревали. Теперь они обновляются раз в час с сайта Нацбанка РК, при сбое — с резервного источника. Каждый ответ проверяется на правдоподобие, последний удачный курс сохраняется на диск и используется при недоступности обоих источников. Администратор может закрепить курс вручную через .env.
  • Общий дедлайн ИИ: на весь ответ ELLA, включая повторы и вызовы инструментов, отводится 40 секунд. Повтор не запускается, если времени на него не хватит. Если посетитель закрыл вкладку, запрос к OpenAI отменяется (AbortSignal), чтобы не тратить деньги впустую.
  • Фото товаров: сервер больше не подставляет «похожее» стоковое фото по названию (зубная щётка получала фото стоматологического приёма). Без фото показывается нейтральная заглушка. Попутно исправлена кнопка «Убрать фото».
  • Витрина: при недоступности каталога показывается блок «Каталог временно недоступен» с кнопками «Попробовать снова» и «Написать в WhatsApp» вместо служебного текста для разработчика.

6.4. Этап 4 — загрузка файлов и контакты

  • Ошибки загрузки файлов (модуль lib/uploadErrors.js): английские сообщения библиотеки multer заменены русскими с реальными лимитами («Фото больше 5 МБ»). Используются корректные HTTP-коды: 413 — размер, 415 — тип файла, 400 — прочее; сбои диска возвращают 500 и пишутся в журнал.
  • Централизация контактов: номер WhatsApp, Instagram, адрес и ссылка на карту были продублированы в 9 местах кода. Теперь они хранятся в одном файле (config/contacts.defaults.json) и переопределяются через .env. Сервер передаёт их клиенту через тег <meta>, поэтому смена номера не требует пересборки сайта. Некорректный номер не даёт серверу запуститься.
  • Найденная попутно ошибка: файл настроек .env загружался позже модуля реквизитов, из-за чего реквизиты компании из .env молча игнорировались. Исправлено: .env загружается первым.

6.5. Пример исправления

До исправления (чат при любой ошибке подменял ответ ИИ шаблоном):

if (response.ok && data.reply) {
  reply = data.reply;
} else {
  reply = replyTo(clean, cache);   // шаблонный «ИИ-ответ» при любой ошибке
}

После исправления сервер журналирует причину и возвращает посетителю код ошибки и идентификатор запроса, а клиент показывает честное сообщение с кнопкой «Повторить»:

if (code !== "bad_request") {
  logger.error("ella.chat", { ...logger.requestMeta(req), code, error });
}
res.status(isElla ? error.status || 500 : 500).json({
  error: ELLA_PUBLIC_ERRORS[code] || ELLA_PUBLIC_ERRORS.internal,
  code,
  requestId: req.id,
});

7. Контейнеризация (Docker)

Для переносимого развёртывания проект упакован в Docker. Сайт запускается на любом сервере одной командой docker compose up -d --build, без установки Node.js и компиляторов.

РешениеЗачем
Многоэтапная сборка (3 этапа)Отдельно собирается React-клиент и компилируются нативные модули (better-sqlite3). В итоговый образ попадает только необходимое, без компиляторов и dev-зависимостей.
Запуск от непривилегированного пользователя nodeБезопасность: процесс в контейнере не имеет прав root.
Именованные тома (volumes)База данных и фото хранятся вне образа и сохраняются при пересборке и обновлении.
Проверка здоровья (HEALTHCHECK)Docker регулярно опрашивает /api/health и видит, если приложение перестало отвечать.
Корректная остановкаПроцесс-инициализатор (init: true) передаёт сигнал SIGTERM, сервер завершает запросы и закрывает базу без потери данных.
Секреты не попадают в образФайл .env исключён из сборки и подключается только при запуске.
Скрипт переноса данныхdb/importLocal.js копирует существующую базу в контейнер через backup API SQLite — без потери записей из журнала WAL.
Ротация логовЖурнал контейнера ограничен (5 файлов по 10 МБ) и не переполнит диск.

8. Тестирование

8.1. Автоматические тесты

Написан набор интеграционных тестов scripts/verify-shop.js (команда npm run verify:shop). Тест запускает настоящий сервер на временной базе данных и проверяет его поведение через HTTP, включая сценарии сбоев. Количество проверок росло вместе с исправлениями: 29 → 32 → 42 → 48.

Основные группы проверок:

  • заказы: корректная сумма, списание и возврат остатка, лимиты количества, валидация телефона, идемпотентность;
  • безопасность: защита админ-методов, лимит попыток входа, запрет слабого пароля в production;
  • ошибки: формат ответа 500 с requestId, понятные ошибки загрузки файлов, приём ошибок из браузера;
  • курсы валют: разбор ответов Нацбанка и резервного источника, отбраковка неправдоподобных значений, кэш на диске;
  • ИИ: дедлайн и отмена запроса на «зависающем» имитаторе OpenAI;
  • запуск: понятная ошибка при занятом порте, отказ запуска при некорректных контактах.

Отдельный тест scripts/verify-ella-core.js проверяет ядро ИИ-ассистента: инструменты, формирование ответа и HTTP-контракт с реальным вызовом OpenAI.

9.2. Что нужно сделать перед запуском в эксплуатацию

  • Задать надёжный пароль администратора (не менее 12 символов) — иначе сервер в режиме production не запустится. Это сделано намеренно.
  • Заполнить реквизиты компании (ИИН/БИН, IBAN) — без них счета не формируются.
  • Разместить сайт за HTTPS (nginx или Caddy) и включить настройку TRUST_PROXY.

9.3. Направления развития

  • Устранить оставшиеся проблемы уровня Low.
  • Подключить внешний сервис мониторинга ошибок (например, Sentry).
  • Добавить сквозные (end-to-end) тесты интерфейса в браузере.

10. Заключение

В ходе работы проведена проверка логики магазина и сквозной аудит обработки ошибок веб-сайта стоматологической клиники. Найдено 27 проблем, из них исправлена 21, включая все проблемы уровней High и Medium. Главный результат — система больше не скрывает сбои: при отказе ИИ, источника курсов валют, загрузки файлов или каталога пользователь получает честное понятное сообщение, а владелец — запись в журнале с идентификатором запроса.

Кроме того, курсы валют стали обновляться автоматически, ИИ-ассистент получил ограничение времени ответа, контакты клиники собраны в одном месте, а приложение упаковано в Docker-контейнер с сохранением данных и корректной остановкой. Все изменения подтверждены автоматическими тестами (48 из 48) и проверкой собранного Docker-образа. Поставленная цель — подготовить проект к эксплуатации — достигнута.

Приложение А. Инструкция по запуску

Локальный запуск

npm run install:all     # установка зависимостей сервера и клиента
npm run build           # сборка React-клиента
npm start               # запуск сервера: http://localhost:3000

Запуск в Docker

docker compose up -d --build     # собрать и запустить
docker compose logs -f           # просмотр журнала
docker compose down              # остановить (данные сохраняются)

Запуск тестов

npm run verify:shop

Админ-панель доступна по адресу http://localhost:3000/admin. Пароль задаётся в файле .env (параметр ADMIN_PASSWORD).
